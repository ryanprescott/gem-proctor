# P1.5 – LLM layer (build spec)

> Companion to [`SPEC.md`](SPEC.md) (v0.23). This file says **what P1.5 builds and how it's checked**. Where the two disagree, `SPEC.md` wins. Fix the discrepancy here, or log a change in SPEC §15.
> Written for a single uninterrupted build ("zero-shot"), **one feature at a time**: each feature ends with its own audit section and its own commit before the next one starts (§10).

---

## 1. Goal

The model-agnostic LLM layer that P2 (authoring), P2.1 (`verify.solve`) and P3.1 (analysis) call: `packages/llm` with the `LlmRuntime` interface, admin-managed endpoints with encrypted keys, role assignments, model discovery and a probe, a fair per-endpoint queue, both structured-output modes with normalization and the repair loop, embeddings with the truncation guard, versioned prompts, call logging, stats and an eval harness. Verified against the reference local setup (Qwen + `embeddinggemma-2` on Ollama, on the 3060 box) and, where a key is available, one cloud model. No user-facing feature calls a model yet.

Source: SPEC §14, row P1.5; §3B (LLM layer), §3C.2 (embedding model, truncation), §1.3 (audit, privacy), §5.1 (admin), §8.1 (role hidden when unassigned), §11.2; [`docs/prompts/authoring-generate.md`](prompts/authoring-generate.md) (probe findings the runtime must support).

## 4. Database (P1.5 tables)

From SPEC §10, plus the columns P1.5 needs (logged in SPEC §15.2 at the end of the phase):

```
Endpoint(id, label, provider, baseUrl?, apiKeyCiphertext?, location: local|cloud, server?, concurrency, timeoutMs,
         createdBy, createdAt, updatedAt, deletedAt?)
RoleAssignment(role PK, endpointId, model, capabilities jsonb, embedding jsonb?, params jsonb?, updatedBy, updatedAt)
LlmCallLog(id, endpointId, model, role?, kind: call|probe|eval, promptId?, promptVersion?, mode, finishReason?, outcome,
           errorCode?, repairAttempts, normalizationFixes jsonb, usage jsonb, queuedMs, latencyMs, actorId?, evalRunId?, at,
           requestBody jsonb?, responseBody jsonb?)
LlmEvalRun(id, evalSet, role, endpointId, model, promptVersion, status: queued|running|done|failed, trials,
           summary jsonb?, items jsonb?, errorCode?, startedBy, createdAt, startedAt?, finishedAt?)
```

- `apiKeyCiphertext`: `base64(iv ‖ ciphertext ‖ tag)`, AES-256-GCM, a fresh 12-byte IV per write, the endpoint id as associated data (a ciphertext copied to another row doesn't decrypt).
- **Endpoints are soft-deleted** (`deletedAt`), so call logs and eval runs keep a valid `endpointId`. A deleted endpoint is hidden from the UI and can't be assigned; deleting one that a role uses is 409 `llm_endpoint_in_use`.
- `RoleAssignment` has one row per role (`role` is the primary key, a check constraint mirrors the `ModelRole` enum). `embedding` is required for the `embeddings` role and rejected for the others (Zod and a check constraint).
- `LlmCallLog` is **append-only like `AuditLog`**: `gem_app` has `INSERT, SELECT` only. It's the provenance record (§3B.4); nothing updates it. No retention job in P1.5.
- `requestBody` / `responseBody` hold the messages, schema and parameters sent and the raw text or object returned, never headers or keys. They're set for `authoring.*` and `verify.solve` calls (and eval runs of those roles); null for `analysis`, `embeddings` and probes.
- `gem_app` gets `SELECT, INSERT, UPDATE, DELETE` on `endpoint`, `role_assignment`, `llm_eval_run` (grants migration, like P0/P1).
- Admin actions on these tables write `AuditLog` rows (§5).

## 5. Decisions made for P1.5

These were left open in SPEC; P1.5 settles them. If one doesn't hold up, change it and log it in SPEC §15.2.

| Decision | Choice | Resolves |
|---|---|---|
| Framework | Vercel AI SDK (`ai`, current major, pinned), wrapped by `packages/llm`; nothing outside `packages/llm` imports `ai` or a provider package (a lint/grep check in CI). If a needed request option can't be sent through the SDK, activate the §15.1 contingency (direct `openai`-SDK adapter) **for that provider only** and log it | §3B.1, §15.1 |
| Providers | `openai-compatible` (`@ai-sdk/openai-compatible`; local servers, gateways and OpenAI-compatible clouds) and **`anthropic`** (`@ai-sdk/anthropic`) as the one first-party cloud adapter. A provider is one file in a registry: `{ id, create(endpoint, key), discoverModels?, reportedContext? }`. `baseUrl` is required for `openai-compatible`, optional for the others | §3B.1, §3B.2 |
| `server` quirks | Per `server` value, in the provider adapter only: discovery and reported context (`ollama`: `/api/show` `num_ctx`; `vllm`: `/v1/models` `max_model_len`; `llamacpp`: `/props` `n_ctx`); `llama.cpp` in `LLM_DEV_SERVER` is accepted as an alias for `llamacpp`. Model behaviour (thinking off, sampling) is **never** a quirk: it lives in `RoleAssignment.params` | §3B.2, §3B.3 |
| `params` | Free-form object, merged into the request body by the adapter (sampling: `temperature`, `top_p`, `top_k`, `presence_penalty`; extras such as Ollama's `reasoning_effort: "none"`). The reference assignment for `qwen3.5-9b-32k` is `{ temperature: 0.7, top_p: 0.8, top_k: 20, presence_penalty: 0, reasoning_effort: "none" }` (prompts doc §4) | §3B.3 |
| Prompt input | `PromptInput = { promptId, vars, messages? }`. The runtime renders the role's template (`packages/llm/prompts/<promptId>/<version>.md` with `{{var}}` placeholders; a missing or unused var throws) and records `promptId@version`. The active version is a constant per prompt in code (changed by review), not a setting | §3B.4 |
| Per-model variants | A variant is a file `<version>.<model-glob>.md`, chosen when the assigned model matches the glob; none ship. The chosen file is recorded in the call log | §3B.4 |
| `LlmResult` | SPEC's fields plus `callLogId`, `promptVersion`, `mode`, `normalizationFixes`, `queuedMs`, and `failedItems` when salvage applies | §3B.1 |
| Repair loop | Normalize (`normalizeQuiz`'s JSON-extraction steps, factored into a shared `extractJson` in `packages/shared`: fences, `<think>` blocks, leading/trailing prose, trailing commas) → Zod. On failure re-ask with the `output-repair` prompt (`output-repair-v1`, written in F2: the Zod issues, the invalid output, the schema), up to `maxRepairs` (default 2, per call option). Normalization fixes are recorded but aren't repairs | §3B.3 |
| Per-item salvage | Opt-in per call: `salvage: { path: "questions" }`. If the whole object still fails after repairs, each element at `path` is validated alone: valid items are returned, invalid ones go to `failedItems` with their Zod issues. Nothing valid → `llm_output_invalid` | §3B.3 |
| `native_schema` | The Zod schema's JSON Schema (`packages/shared`'s exporter) is sent as the provider's structured-output format (`response_format: json_schema` for `openai-compatible`), in schema property order (llama.cpp writes properties in order, prompts doc §4). `prompt_only`: the schema and one example are appended to the system message | §3B.3 |
| Streaming | `streamObject` yields partial objects and resolves `final` through the same normalize → validate → repair path (repairs are non-streamed re-asks). Used by P2's generation; P1.5 tests it against the mock server | §3B.1 |
| Queue | In-process (single API instance, SPEC §5.3), one per endpoint, rebuilt when the endpoint is edited (in-flight calls finish). Fair: round-robin across caller keys (`userId`, or `system` for jobs), FIFO within a key. `timeoutMs` counts from dispatch; queue wait is unbounded but cancellable through an `AbortSignal`, and logged as `queuedMs` | §3B.2 |
| Errors | Typed `LlmError` with codes: `llm_role_unassigned`, `llm_cloud_blocked`, `llm_endpoint_unreachable`, `llm_endpoint_auth`, `llm_endpoint_timeout`, `llm_endpoint_error` (non-2xx, with status), `llm_output_invalid`, `llm_embedding_truncated` (with the input's index), `llm_context_exceeded` (prompt estimate > `contextWindow − maxOutputTokens`, checked before sending). No automatic retry on transport errors in P1.5 | §1.3, §3B.3 |
| Embeddings | `embed(texts, { kind: "query" \| "document" })` prepends `queryPrefix` / `documentPrefix` to the sent text only, batches up to 32 inputs, and returns `{ vectors, tokens[] }`. A text whose estimate (chars ÷ 3) is over half of `maxInputTokens` is sent **alone**, so its `usage.prompt_tokens` is exact; a text whose count reaches `maxInputTokens` fails `llm_embedding_truncated`. A vector whose length isn't `dimensions` fails `llm_endpoint_error` | §3B.2, §3C.2 |
| Probe | `POST /admin/llm/endpoints/:id/probe { model, kind: "chat" \| "embeddings" }`. Chat: one tiny structured request in `native_schema`, then `prompt_only` if that fails; reports latency, schema respected per mode, `finishReason`, reported context. Embeddings: dimensions, latency, and **measured `maxInputTokens`**: two inputs that differ only after token *n*, searched (doubling, then bisection, ≤ 16 requests, up to 32,768) for the largest *n* where the vectors still differ (cosine < 0.999999) and `prompt_tokens` still grows. Nothing is saved; the UI offers "Use these values" for a role | §3B.2 |
| Local endpoints only | `InstanceSettings.localEndpointsOnly: boolean` (default `false`). While on: the runtime refuses a call whose role resolves to a `cloud` endpoint (`llm_cloud_blocked`, logged), `PUT /admin/llm/roles` to a cloud endpoint is 409 `llm_cloud_blocked`, and turning it on while a role is on a cloud endpoint is 409 `llm_cloud_roles_assigned` with the roles listed | §3B.2 |
| Role status for users | `GET /llm/roles` (any signed-in user): per role `{ role, assigned, location?, endpointLabel? }` (label only for `cloud`), no URLs or model ids. P2/P3.1 use it to hide unassigned features and show the cloud notice (§8.1) | §3B.2, §8.1 |
| Audit actions | `llm.endpoint.create`, `llm.endpoint.update`, `llm.endpoint.delete`, `llm.endpoint.secret_change` (fact only: `{ set: true }` / `{ cleared: true }`), `llm.role.assign`, `llm.role.unassign`; `settings.update` covers `localEndpointsOnly`. `before`/`after` never contain a key or ciphertext. Probes and eval runs are not audited (they're in `LlmCallLog`) | §1.3 |
| Secret key | Saving a key without `ENDPOINT_SECRET_KEY` configured is 409 `llm_secret_key_missing`. At startup, if any endpoint has a ciphertext and the key is missing or doesn't decrypt it, the API logs the endpoint ids and the runtime treats those endpoints as `llm_endpoint_auth` (it doesn't refuse to start) | §3B.2 |
| SSRF | Only admins create or edit endpoints (SPEC). `baseUrl` must be `http:` or `https:` with no credentials in it. No address block-list in v1 (local endpoints are private addresses by design) | §3B.2 |
| Rate limits | `@fastify/rate-limit` on probe, discovery and eval-run routes (per admin, e.g. 30/min), as SPEC asks for model-calling endpoints | §11.2 |
| Eval sets | Files in `packages/llm/evals/<name>/` (`eval.json`: role, prompt, request, fixtures, metrics). P1.5 ships two: **`generate-smoke`** (`authoring.generate`, the current `gen-v8` prompt + `strict7` schema, one fixture chunk on inner products written for the repo, 3 calculation + 1 concept question per trial; metrics: valid first try, repairs per call, valid after repairs, evidence quote found verbatim in the chunk, seconds per question) and **`retrieval-mini`** (`embeddings`, ≥ 14 fixture chunks and ≥ 15 queries with expected chunk; top-1 and MRR, with and without prefixes, cosine only, no pgvector). P2 and P2.1 add metrics (grounding, coverage, L7) to the same harness | §3B.4, §3C.2 |
| Eval runs | `POST /admin/llm/evals/run { evalSet, trials? }` queues a pg-boss job against the role's **current** assignment; one run at a time per role (409 `llm_eval_running`). `GET /admin/llm/evals` and `/:id` return status and the report; the UI polls. CLI: `bun run llm:eval <set> [--trials n]` runs the same runner and prints the report (uses the DB's assignments, or `LLM_DEV_*` with `--dev`) | §3B.4, §12 |
| Stats | `GET /admin/llm/stats?since=` per role × endpoint × model: calls, failures by code, repair rate, salvage rate, p50/p95 latency, p95 queue wait, tokens in/out. Computed with SQL over `LlmCallLog` | §3B.2, §12 |
| Dev seed | `bun run llm:seed` (and on API start when `NODE_ENV=development`): creates the `LLM_DEV_*` endpoint and, if `LLM_DEV_EMBED_BASE_URL` differs, a second one for embeddings; assigns `LLM_DEV_ROLES` and `embeddings` if they're unassigned. Never overwrites an existing assignment. Writes audit rows with a null actor | P0.md §5 |
| Live checks | Model servers aren't in CI. CI uses a **mock OpenAI-compatible server** (`Bun.serve`) that can emulate each `server` value's discovery/context endpoints, structured and unstructured replies, invalid JSON, `<think>` leaks, slow replies, errors and silent embedding truncation at a set cap. Live runs (`bun run llm:live`) are separate and recorded in the audit | §3B.4 |

## 6. Routes in P1.5

All under `/api/v1`, each with a shared Zod contract and a Casbin declaration. New object types `llm_endpoint`, `llm_role`, `llm_eval`, `llm_stats` (admin only, through the `*` line; no proctor rows) and `llm_status` (student+, `read`).

```
Admin   GET    /admin/llm/endpoints                       list (no keys; `hasKey: boolean`)
        POST   /admin/llm/endpoints                       { label, provider, baseUrl?, apiKey?, location, server?, concurrency?, timeoutMs? }
        GET    /admin/llm/endpoints/:id
        PATCH  /admin/llm/endpoints/:id                   same fields; apiKey: string sets, null clears, absent keeps
        DELETE /admin/llm/endpoints/:id                   soft delete; 409 llm_endpoint_in_use
        GET    /admin/llm/endpoints/:id/models            discovery; 409 llm_models_unsupported where the server has none
        POST   /admin/llm/endpoints/:id/probe             { model, kind }
        GET    /admin/llm/roles                           every ModelRole, assigned or not
        PUT    /admin/llm/roles/:role                     RoleAssignment body
        DELETE /admin/llm/roles/:role
        GET    /admin/llm/stats?since=
        POST   /admin/llm/evals/run                       { evalSet, trials? }
        GET    /admin/llm/evals?role=                     runs, newest first
        GET    /admin/llm/evals/:id
Users   GET    /llm/roles                                 role status (§5)
```

`GET/PUT /admin/settings` gains `localEndpointsOnly`. SPEC §12's `GET/PUT /admin/llm/roles` becomes per-role `PUT`/`DELETE` plus `GET /admin/llm/evals[/:id]` and `GET /llm/roles` (logged in SPEC §15.2).

New error codes (each with an `errors:<code>` catalog entry): `llm_role_unassigned`, `llm_cloud_blocked`, `llm_cloud_roles_assigned`, `llm_endpoint_unreachable`, `llm_endpoint_auth`, `llm_endpoint_timeout`, `llm_endpoint_error`, `llm_endpoint_in_use`, `llm_models_unsupported`, `llm_output_invalid`, `llm_context_exceeded`, `llm_embedding_truncated`, `llm_secret_key_missing`, `llm_eval_running`.

Web pages: admin gains an **LLM** page (`/admin/llm`): endpoints table + create/edit dialog (key field write-only, "key set" state, clear action), per-endpoint models list and probe panel, roles table (endpoint, model, mode, context, cloud badge; edit dialog prefilled from a probe), the "Local endpoints only" switch with its 409 explained, stats table, eval runs (start, status, report). Every cloud-assigned role shows a notice naming the endpoint.

## 7. Build order (one commit per feature)

Each feature is finished, tested, audited and committed before the next starts (§10). The commit message names the feature: `P1.5: <feature>`.

1. **F1 LLM data, secrets & authz** (`packages/db`, `packages/authz`, `packages/shared` contracts + error codes, secret crypto): S1, S2, S8's setting field, contracts for every §6 route, audit action names. Criteria C1–C6.
2. **F2 Runtime** (`packages/llm`): S3–S7, S8's enforcement, the mock server, `extractJson` factored out of the normalizer, and S10's template loader (rendering, variant choice) with the `output-repair` prompt, since `generateObject` takes a `PromptInput`. Criteria C7–C19, C29.
3. **F3 Admin API & seed** (`apps/api`): S9, S13, rate limits, audit rows; authz matrix extended. Criteria C20–C27.
4. **F4 Prompts & evals** (`packages/llm/prompts`, `packages/llm/evals`, runner, job, CLI): the rest of S10 (moving the drafted prompts in), S11. Criteria C28, C30–C32.
5. **F5 Admin LLM UI** (`apps/web`): S12, with Playwright + axe. Criteria C33–C37.
6. **F6 Live verification & phase close**: C38–C42, SPEC update (§10), `docs/DEVELOPMENT.md`.

## 8. Acceptance criteria (the audit checklist)

Each line is checked by a test, a command, or reading the code. The audit marks each **pass / fail / partial / blocked** with evidence. P0's A1–A33 and P1's B1–B38 must keep passing; a P1.5 change that breaks one is a P1.5 failure.

**F1 LLM data, secrets & authz**
- [ ] C1 Migration creates the four §4 tables with their constraints: role check, `embedding` only on `embeddings`, FK to non-deleted endpoints enforced in the API (soft delete), `LlmCallLog` indexes on `(at)` and `(role, endpointId, model, at)`.
- [ ] C2 `gem_app` can read and write `endpoint`, `role_assignment`, `llm_eval_run`; on `llm_call_log` an `UPDATE` or `DELETE` as `gem_app` fails; `audit_log` grants unchanged (A21).
- [ ] C3 Secret crypto: round-trip; a fresh IV per write (two encryptions differ); a tampered ciphertext, a wrong key, or a ciphertext moved to another endpoint id fails to decrypt.
- [ ] C4 `Endpoint`, `RoleAssignment` (with `capabilities`, `embedding`, `params`) and `ModelRole` are Zod schemas in `packages/shared` matching SPEC §3B.2; no response contract includes `apiKey` or the ciphertext (a test walks every admin LLM response schema).
- [ ] C5 Every §6 route has a contract and a declaration; the startup check (A16) covers them.
- [ ] C6 `InstanceSettings.localEndpointsOnly` defaults to `false`; existing settings rows still load.

**F2 Runtime** (all against the mock server unless stated)
- [ ] C7 `generateObject` in `native_schema` sends the JSON Schema as `response_format` with properties in schema order, and returns a typed value with every `LlmResult` field.
- [ ] C8 `prompt_only` puts the schema and example in the system message; a reply wrapped in prose, a code fence or a `<think>` block is extracted, and the fixes appear in `normalizationFixes` with `repairAttempts: 0`.
- [ ] C9 Repair loop: invalid → valid on the 1st and 2nd repair (`repairAttempts` 1 and 2; the repair request contains the Zod issues and the invalid output); still invalid after `maxRepairs` → `llm_output_invalid`.
- [ ] C10 Salvage: a batch with 3 valid and 1 invalid item returns 3 values and 1 `failedItems` entry; all invalid → `llm_output_invalid`.
- [ ] C11 `streamObject` yields partial objects in order and its `final` goes through validation and repair like `generateObject`.
- [ ] C12 `params` reach the request body unchanged (the mock captures `reasoning_effort: "none"`, `presence_penalty: 0`, `top_k: 20`); shared code contains no model or server names (grep check).
- [ ] C13 Queue: with `concurrency: 1`, two callers × 3 calls each are dispatched alternately and never more than one in flight; `concurrency: 2` allows two; an aborted queued call never reaches the server; `timeoutMs` → `llm_endpoint_timeout`; `queuedMs` is logged.
- [ ] C14 Each error code in §5 is produced by its mock scenario (connection refused, 401, slow reply, 500, oversized prompt, unassigned role) and is an `LlmError`, never a raw SDK error.
- [ ] C15 Embeddings: prefixes are sent but never returned or stored in the result; batches ≤ 32; a long text is sent alone; a text at the mock's truncation cap fails `llm_embedding_truncated` with its index; a wrong vector length fails.
- [ ] C16 Call log: one row per call (repairs counted in that row), bodies present for `authoring.generate` and `verify.solve` and null for `analysis` and `embeddings`; no row or body contains the API key (the mock's key is searched for in every logged column).
- [ ] C17 Local endpoints only: a call on a cloud-assigned role fails `llm_cloud_blocked` without any request reaching the mock, and is logged.
- [ ] C18 `anthropic` adapter: requests go to its (mocked) base URL with the key header, structured output works, `params` pass through; adding a provider needs only a registry file (read the code).
- [ ] C19 Only `packages/llm` imports `ai` or `@ai-sdk/*` (CI check, part of `bun run ci`).
- [ ] C29 Template rendering: a missing var, an unknown var, and a variant file chosen by model glob are each tested; the call log records `promptId@version` and the variant file.

**F3 Admin API & seed**
- [ ] C20 Endpoint CRUD: create/edit/delete with audit rows (`before`/`after` without secrets); `apiKey` set / keep / clear semantics; `secret_change` row on set and clear; deleting an endpoint in use is 409; a deleted endpoint can't be assigned.
- [ ] C21 Discovery returns the mock's models for `openai-compatible`; 409 `llm_models_unsupported` where the mock has no models endpoint.
- [ ] C22 Probe chat: reports latency, schema respected per mode, reported context for `ollama`, `vllm` and `llamacpp` mocks. Probe embeddings: dimensions, and `maxInputTokens` measured within ±5% of the mock's cap in ≤ 16 requests.
- [ ] C23 Roles: `GET` lists all six roles; `PUT` validates `capabilities` and `embedding` (required for `embeddings`, rejected for others) and writes `llm.role.assign`; `DELETE` writes `llm.role.unassign`.
- [ ] C24 Local-only rules: assigning a cloud endpoint while on → 409 `llm_cloud_blocked`; turning it on with a cloud role → 409 `llm_cloud_roles_assigned` listing roles; the change is audited as `settings.update`.
- [ ] C25 `GET /llm/roles` for a student shows assigned state and a cloud endpoint's label only; no URLs, models or ids.
- [ ] C26 Authz matrix (A17 extended): anonymous, student, proctor, admin × every §6 route: only admins reach `/admin/llm/*`; every signed-in user reaches `/llm/roles`. Rate limits answer 429 on probe and discovery.
- [ ] C27 `llm:seed` creates the dev endpoint(s) and assignments from `LLM_DEV_*` once; a second run changes nothing; an existing assignment is never overwritten; `llama.cpp` is accepted as `llamacpp`.

**F4 Prompts & evals**
- [ ] C28 `packages/llm/prompts/` has `authoring.generate` (`gen-v8`), `verify.solve` blind (`blind-v2`) and classify (`classify-v1`), `program-repair` (`repair-v1`) and `output-repair` (`output-repair-v1`, from F2), with their version ids; `docs/prompts/authoring-generate.md` and the probe README point at them; the strict7 schema is a Zod schema in `packages/shared` whose JSON Schema matches the probe's `SCHEMAS["strict7"]` (or each difference is listed in the audit).
- [ ] C30 `generate-smoke` and `retrieval-mini` run against the mock (deterministic replies) and produce reports with every §5 metric; a report is stored on `LlmEvalRun` with `status: done`.
- [ ] C31 Eval runs: `POST /admin/llm/evals/run` queues a job, a second run for the same role is 409 `llm_eval_running`, a model failure ends the run `failed` with a code; calls made by the run carry `evalRunId`.

## 10. Build and audit procedure (per feature)

For each feature F1–F5, in order:

1. Build it, with its tests. Keep `SPEC.md` in mind: a decision in §5 that turns out wrong is changed here and noted for the SPEC log.
2. Run `bun run ci`. It must pass in full (P0 and P1 criteria included); fix anything it reports before going on.
3. Audit the feature's criteria from §8 and **append** a section `## F<n> <name>` to `docs/P1.5-audit.md`: a table with pass / fail / partial / blocked and evidence (test name, command output, or file:line) per criterion, the `bun run ci` summary, and any deviations from SPEC or this file. A `fail` is fixed before the commit; a `blocked` says what unblocks it.
4. Commit on `main` with only that feature's changes plus its audit section: `P1.5: <feature>` (e.g. `P1.5: LLM data, secrets and authz`), a body listing what was built, and the attribution line. Don't start the next feature with failing checks or uncommitted work.
5. If a later feature has to change an earlier one, that change goes in the later feature's commit, and the earlier audit row is updated in the same commit with a note.

Then **F6**: run the live checks C38–C40 (record model, server version, tags, `params`, and the reports), check C41–C42, re-run every earlier criterion that the later features touched, write the summary table at the top of `docs/P1.5-audit.md` (counts per result, blocked list, deviations), update SPEC (bump to v0.24, add the "Last updated" entry, log §5 decisions in §15.2, update §3B, §10, §12, and SPEC §13 Q5 with what C38–C40 measured), update `docs/prompts/authoring-generate.md` §4 with the live `generate-smoke` row, and commit `P1.5: phase audit; spec v0.24`.
