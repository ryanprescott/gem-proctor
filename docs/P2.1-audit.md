**Deviations and notes.**
- **The parent is single-threaded**, with a `selectors` loop, and runs **one child at a time**. The skeleton's thread per connection would have forked from a threaded process, and blocking on a child would have failed `/health` for up to 10 s. One child at a time also removes any interaction between two children, which share the `runner` uid. With `cpus: 1.0` nothing is lost. Health is answered while a child runs (`test_health_while_a_child_runs`).
- **Killing a child needs a trick:** with `cap_drop: ALL`, root can't signal `runner` (that takes `CAP_KILL`), and SPEC allows only `SETUID`/`SETGID`. The parent sets its effective uid to `runner` for the `killpg` call and back. A child can't use the window, because the kernel checks the target's real and saved uids, which stay 0. The sleep test in the container is what proves it: `timeout` at 10,005 ms.
- **`RLIMIT_FSIZE` is 0 in every case**, so no run can write a byte, in `/tmp` or anywhere, which is what SPEC's step 2 says ("no file writes"). P2.1.md §5 leaves room for a `/tmp` case; C6 is satisfied without one. A run can still create an empty file in the sticky `/tmp`; "C6" shows its size is 0, and recycling removes it.
- **`/etc/passwd` and `/etc/group` are mode 0640 in the image.** World-readable, they'd hold nothing secret, but the read would succeed unnoticed. Unreadable, it's a denial, so the injection signal fires.
- **Denial detection** adds to §5's list, for what SPEC's programs actually raised: `socket.gaierror` (DNS), `ECONNREFUSED` (a connect on loopback, which `network_mode: none` still has), `EHOSTUNREACH`, `EROFS` and `EFBIG` (writes), `EMFILE`, `EAGAIN`. A program that catches the error itself and carries on is not flagged: it gained nothing, and SPEC's classification is by what happened.
- **`os.system`** returns a status with nothing run (32512; "os.system ran nothing" confirms no file), and `ctypes` loads and its calls fail (`setuid(0)` and `kill(1, 9)` return -1). Those programs end `ok` with those values: the isolation stops them, and they aren't denials by §5's rule. `sympify` on a string runs its `eval` in the child, as `runner` (10002): that's the expected end.
- **A timeout is an anomaly too** ("a child killed by a limit"), and `SIGXCPU` is `timeout`, not a denial: a slow honest program shouldn't raise the injection signal. A program that ignores `SIGXCPU` dies at the hard limit (6 s) as `sandbox_denial`.
- A program's `print` goes to a no-op writer, since fds 0–2 are closed. `result` of an unsupported type is `program_error` / `ResultTypeError`, so the repair loop (F2) can treat it as "wrong result type".
- A child calls `gc.freeze()` first. Found by the tests: stale socket or selector objects inherited from the parent, finalized in the child, closed their fd numbers, which by then could be the result pipe's, and the run ended with an empty reply.
- OpenBLAS threads are limited in `gem_verify/__init__.py`, before NumPy loads. Otherwise it maps per-thread buffers (1.2 GB of address space here), against a 512 MB limit, and starts threads a child can't restart.
- **`check-compose.ts` had never been run** (P0's A33 was blocked), and on its first run it failed: the Python image sets `GPG_KEY`, the public id of its release key, which matched the secret-name check. Exempted by name; the entrypoint's `env -i` keeps it from the process anyway.
- The suite's restarts: Docker doubles the delay after each quick exit, up to a minute, so past the first two (which watch the policy) it runs `docker compose restart` if the service isn't back in 4 s. Local tests and `bun run e2e` use `superviseVerify` for the same job.
- `recycleEvery` reaches the parent in each request (`envelope` in `verify.ts`), since the runner has no database. F3 wires it to the setting.
- `biome.json` skips the generated `contract.json`, like `packages/shared/schema`.

**Changed in F2 (P2.1.md §10 step 5).**
- C4/C7: `server.py` imported NumPy before the package could limit its threads, so on the real entrypoint (not in unit tests, which load the package first) OpenBLAS took most of a child's address space. It surfaced as `MemoryError` on LaTeX options. The import order is fixed, with a test through the real entrypoint in `verify-client.test.ts`; `verify:escape` re-ran 40/40 on the fixed image.
- C10: `compare` reads `-3e_1 + 8e_2 + e_3` as the vector `[-3, 8, 1]` (sample Q14), and a value that can't be read back equals nothing rather than failing the run.
- C11: after half the constraint's draws, sampling tries positive values. See F2's notes.

**Deviations and notes.**
- **Spec decision changed: sampling and `min(c) > 0`.** The prompt's own example constraint is `valid = min(c) > 0`, and the model copies that form. SPEC's default of "at least one negative entry" makes it impossible, so 2 of 4 live runs while recording failed `constraint_unmet` on honest questions. After half the constraint's draws (25), sampling now tries positive entries. Unconstrained draws keep SPEC's defaults (C11). For SPEC §15.2.
- **`multi_choice` and `short_answer` in flow A.** `GeneratedQuestion` (the `strict7` schema) has no computable `short_answer` branch, and the P1.5 test pins that schema. Flow A takes its own `ComputableQuestion`, so C16 runs on it; whether the model can emit one is P2's schema change.
- **Options that are all prose** (sample Q9, "What does $q^T p$ represent?") have no value to compare, so whatever the classification says they go to Not computable; a word among numeric options ("Undefined", sample Q4) just can't match. **A number against options written in `n`** (a program that set `n = 5` for a flop count) is Couldn't check, reason `comparison_symbolic`, rather than a false No match. Both came from live recordings, and neither is in SPEC's table: they refine "Couldn't check" and "Not computable".
- `denied` is a seventh outcome beside SPEC's six, since C23 says a denial fails the question. `verification.status` is `failed`.
- `VerificationRun.programKind` stays `author | blind` as §4 says: a mistake program is `author`, with `{ mistake: true }` in `result`. `sample_inputs` isn't a run unless it ends in a denial; then its row carries the constraint, or the author program.
- A run's `matched_option` isn't known until the comparison, and the table is append-only, so a question's runs are written together when its outcome is known (`RunTrail`).
- `importedQuestion` reads the normalized value, so a question that failed `Quiz` validation still works, and a question with no text is Couldn't check with no call.
- The recording's variance is real: over 5 runs, Q7 was Wrong answer with fix `-1` every time, while the flop-count questions (Q10, Q11, Q20) and Q14 went either way on classification. Runs before the fixes had false No match on those, which is what the two refinements above address. The fixture is run 5, and F4's live run measures the rates. One run's questions wrote `{x[0]}` placeholders, so all three disagreed: that's L1's placeholder check, in P2.
