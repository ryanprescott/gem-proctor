# P2.1 – Answer computation & verification (build spec)

> Companion to [`SPEC.md`](SPEC.md) (v0.26). This file says **what P2.1 builds and how it's checked**. Where the two disagree, `SPEC.md` wins. Fix the discrepancy here, or log a change in SPEC §15.
> Written for a single uninterrupted build ("zero-shot"), **one feature at a time**: each feature ends with its own audit section and its own commit before the next one starts (§10).
> **Build order:** P2.1 comes first, then [`P2.md`](P2.md). SPEC §14 only requires it before P2's generation step; nothing in P2.1 needs sources or the knowledge base. Flow A is built and tested here against recorded model output; P2 connects it to real generation.

---

## 1. Goal

For anything computable, the model never decides the answer. This phase builds the sandbox that runs model-written programs, the `verify.solve` calls, option parsing and comparison, the option builder, flow A as an engine, flow B end to end on import, the suggested-fix flow, and the proctored publish gate. The headline test: importing `tests/engr108_chapter1_new_20q_quiz.json` makes Q7 fail with a suggested fix of `-1`, and a creator can confirm it.

Source: SPEC §14 row P2.1; §3A.3.1 (all of it); §2.4; §3D.1 steps 4–6; §4 `verification`; §10 `VerificationRun`; §11.5; `docs/prompts/authoring-generate.md`; `tools/probes/l7/` (`inputs.py`, `distract.py`, `probe.py` are the working prototypes to port).

## 4. Database

```
VerificationRun(id, jobId?, testVersionId?, questionId, programKind: author|blind, program TEXT, status, result jsonb,
                matchedOption?, durationMs, sandboxVersion, at)   // draftQuestionId? is added by P2
VerificationJob(id, ownerId, status: queued|running|done|failed, input jsonb (normalized quiz value), inputHash,
                items jsonb?, summary jsonb?, errorCode?, createdAt, startedAt?, finishedAt?)
```

- `VerificationJob` is new (log it in SPEC §15.2): import preview saves nothing, so a run needs something to hang from before a `TestVersion` exists. A job's rows are private to its owner (and admins).
- `VerificationRun.status`: `ok | program_error | timeout | sandbox_denial | invalid_output`. Append-only for `gem_app` (`INSERT, SELECT`): it's provenance. `verification_job` gets `SELECT, INSERT, UPDATE, DELETE`. Grants in a hand-written migration, like earlier phases.
- `InstanceSettings` gains `verify: { proctoredGate: true, recycleEvery: 500, distractorCount: 3, numericTolerance: 1e-6, sampling: { ... SPEC defaults } }`. A settings row without the key loads with the defaults.

## 5. Decisions made for P2.1

If one doesn't hold up, change it and log it in SPEC §15.2.

| Decision | Choice | Resolves |
|---|---|---|
| Contract | Zod in `packages/shared/src/verify.ts` is the source; its JSON Schema is exported to `apps/verify/gem_verify/contract.json`, staleness-checked by the existing export step. Python validates against it with a small stdlib validator: **no Pydantic**, so the parent stays small and the runner's third-party list stays SPEC's. Log this in §15.2 | §3A.3.1 "Contract" |
| Socket protocol | Newline-delimited JSON, one request per connection, as the skeleton. Request cap raised to 256 KB. Replies stay capped at 64 KB | §3A.3.1 |
| Who may connect | The parent reads `SO_PEERCRED` and refuses a peer whose uid is the `runner` uid, so a child can't reach the parent by path. Socket directory stays writable only by the parent | §3A.3.1 "children can't touch the socket" |
| Privilege drop | In the container the parent is root with only `SETUID`/`SETGID`, and children become `runner` (10002). The Dockerfile passes `--require-privdrop`, and with it the parent refuses to start, or to run a child, if the drop can't happen. Without the flag and not root (local tests, `bun run e2e` with no Docker), it runs children as the same user and logs one warning; the escape suite never runs in that mode | §3A.3.1 |
| Child order | setgid/setuid, rlimits (CPU 5 s, AS 512 MB, FSIZE 0 outside the `/tmp` case in C6, NPROC 0, NOFILE small), clear env, close every fd but the result pipe, then `exec` of the program with `compile` + `exec` in a fresh namespace. Wall clock 10 s in the parent, killing the child's process group | §3A.3.1 |
| Pre-imports | sympy, numpy, lark, and SymPy's LaTeX parser (Lark backend) are imported by the parent before serving, so children don't need file reads for them | §3A.3.1 |
| Author and blind programs | Always separate requests, so always separate children. Sampling may evaluate `constraint` and, for `true_false`, the author program across draws inside one child, because that all belongs to one question; the final author run is a fresh request | §3A.3.1 |
| Sampling | `sample_inputs` runs as one child per question, on a seeded `random.Random`. Port `inputs.py`. Seed = sha256 of `(batch seed, tempId)`; the same seed, inputs and programs give the same output. `used` value sets are passed in and returned, so uniqueness per test is the caller's | §3A.3.1 |
| Input source order | Values parsed from the cited chunks first, in order of appearance, once per test; then `from: "source"`; then sampling, as SPEC | §3A.3.1 |
| Option builder | `build_options` ports `distract.py`, run in a child. Input includes the mistake values from separate `run` requests, each in its own child. Output: options, `correctAnswer`, `verification.distractors` | §3A.3.1 step 5 |
| Comparison | `compare` runs in a child: exact or `simplify(a - b) == 0` (with a 2 s guard), else relative tolerance for floats. The API never evaluates a value | §3A.3.1 "Results" |
| Program repair | One retry per program with `program-repair/repair-v1` for a syntax error, `NameError`, `ImportError` or wrong result type, as the prompts doc proposes (it fixed every failure in the probe). Never for a timeout or a sandbox denial, and never for `mistakes`. Log it in §15.2 | prompts doc §5 |
| Size guard | A program over 4 KB is rejected by the API before sending (`verify_program_too_large`) | §3A.3.1 |
| Recycling | The parent counts runs and exits 0 at `recycleEvery`, and exits at once after an anomaly (a child killed by a limit, a denial, a malformed reply). Compose's `restart: unless-stopped` brings it back with a fresh `tmpfs`. The API holds **no Docker socket**. `VerifyClient` waits for `health` (up to 30 s) and retries the request once; a second failure is `verify_unavailable` | §3A.3.1 |
| Denial detection | The child installs nothing to block access. A denial is classified from what happened: `OSError` with `EACCES`/`EPERM`/`ENETUNREACH`/`EAFNOSUPPORT`, `BlockingIOError` on fork, `MemoryError`, or death by signal. Ordinary math errors stay `program_error` | §3A.3.1 |
| Where L7 lives | `packages/authoring/src/l7/`, framework-free, taking `LlmRuntime`, a `VerifyClient` interface and a run recorder, so tests can use a fake sandbox or the real parent | §11.1 |
| Import job | `POST /imports/preview` stays as it is, synchronous and with no model. New `POST /imports/verify` queues a pg-boss job on the normalized value; `GET /imports/verify/:id` is polled. Questions that fail `Quiz` validation are still checked: the job works on the normalized value, not the validated quiz. Model time on a 20-question quiz is minutes, so it can't be inside preview | §3D.1 step 4 |
| Saving | `POST /imports` takes an optional `verificationJobId` and the accepted fixes. Each `verification` result is copied to the saved question; an accepted fix sets `correctAnswer`, sets `verification.status: "computed"`, and is listed in `TestImportRecord.report`. Rejecting a fix leaves the error in place, so the quiz can't be saved until it's edited | §3D.1 |
| Fix is never automatic | A suggested fix is data until the creator confirms it, for the owner in the UI. A test proves no save path applies one implicitly | §3A.3.1 |
| No `verify.solve` assigned | The import still works: the Verify action is disabled with a reason (from `GET /llm/roles`), and `POST /imports/verify` is 409 `llm_role_unassigned`. Questions keep no `verification`, and the gate counts them as not verified | §8.1 pattern |
| Classification | `verify.solve.classify/classify-v1` on imported questions. A question already marked `computable: false` in the file is still classified, because an imported flag isn't trusted | §3A.3.1 flow B step 1 |
| Publish gate | `InstanceSettings.verify.proctoredGate`, default on. `checkProctorReady(content)` in `packages/authoring` lists computable questions that aren't `computed`. Proctored assignments don't exist yet, so here it's exposed as `proctorReady` + `blockers` on the version response and shown on the test page; P3 calls it on assignment creation. Audit: `settings.update` | §3A.3.1, §13 Q12 |
| Injection signal | A denial fails the question, writes audit action `verify.sandbox_denial` (actor null, target the job or question, no program text in the row beyond its id). Flagging source chunks comes with P2 | §3A.3.1 |
| KaTeX | Rendered results and options use the existing renderer with `trust: false` and size limits | §3A.3.1 |
| gVisor | Dev and CI use the default runtime with the same settings, as SPEC says. `docker/compose.prod.yaml` keeps `runtime: runsc`. **Check when it's installed:** the API reaches the runner over a Unix socket across containers, which gVisor restricts by default, so it may need `runsc --host-uds=open` or similar in `daemon.json`. C36 records the result, or **blocked** | §3A.3.1 |
| Error codes | `verify_unavailable`, `verify_program_too_large`, `verify_job_not_found`, `verify_fix_invalid`; `verification.*` issue codes in the report go through the catalog like `QuizIssue` codes | §1.3 |

## 6. Routes in P2.1

All under `/api/v1`, each with a shared Zod contract and a Casbin declaration. New object type `verification_job` (proctor and admin, owner-scoped, like imports).

```
Imports  POST /imports/verify                  { value } → job { id, status }; rate limited (model-calling)
         GET  /imports/verify/:id              status, per-question results, suggested fixes
         POST /imports                         gains verificationJobId?, acceptedFixes?: [{ questionId, correctAnswer }]
Tests    GET  /tests/:id/versions              each version gains proctorReady, blockers
Admin    GET/PUT /admin/settings               gains verify
```

Web: the Import page gains a **Verify answers** step with live-region progress, a badge per question (Verified, Wrong answer, No match, Ambiguous, Couldn't check, Not computable), both the blind program and its result in a disclosure, and **Accept fix** / **Keep mine** on suggested fixes. The test page shows verification status per question and the proctor-readiness state. Admin settings gain the gate switch.

## 8. Acceptance criteria (the audit checklist)

Each line is checked by a test, a command, or reading the code. The audit marks each **pass / fail / partial / blocked / dropped** with evidence. A1–A33, B1–B38 and the C-numbers of `docs/P1.5.md` (cited here as P1.5-Cn) must keep passing; a change that breaks one is a P2.1 failure.

**F1 Sandbox**
- [ ] C1 `run` returns the serialized value for integers, rationals (`"p/q"`), decimals, vectors, matrices, expressions and booleans, each with LaTeX; a Q7 program returns `-1`.
- [ ] C2 Each run is a new process: two consecutive runs show different pids, and a run can't see a global set by the previous one.
- [ ] C3 A child runs as `runner`, with no capabilities, an empty environment, and only its pipe open (read from inside a child, in the container).
- [ ] C4 Limits: CPU, address space, process count; wall clock kills a sleeping or spinning child and its children at 10 s; result over 64 KB → `invalid_output`.
- [ ] C5 A child can't connect to the parent's socket (peer check), replace it, or signal the parent.
- [ ] C6 `/tmp` written by one run isn't readable by a later run, or the later run's value is unaffected; a write over the limit fails.
- [ ] C7 **Escape suite** (`bun run verify:escape`, real container): every SPEC program (socket, DNS, `/etc/passwd`, env, write outside `/tmp`, over limit, fork bomb, memory, infinite loop, `ctypes`, `os.system`, `sympify` on a string, unlink or replace the socket, signal the parent, leave state then a normal run, 10 MB result, invalid JSON) fails in the expected way, and the next normal run gives the right value.
- [ ] C8 Recycling: exit at `recycleEvery` and after each anomaly; Compose restarts it; the client waits for health and retries once; a second failure is `verify_unavailable`.
- [ ] C9 `parse_options`: plain numbers, fractions, `\frac`, `\sqrt`, `bmatrix`/`pmatrix`, `^T`, expressions such as `2n - 1`; malformed LaTeX is a per-option failure, never a crash.
- [ ] C10 `compare`: `0.5` equals `\frac{1}{2}`, `sqrt(38)` equals `6.1644…` within tolerance, `1` differs from `-1`; a pathological expression hits the guard rather than the wall clock.
- [ ] C11 `sample_inputs`: SPEC's defaults hold over 1,000 draws; textbook values are refused; constraint redraws up to 50, then fails; `true_false` reaches a True target on an orthogonality question, within 2,000 draws; same seed, same output.
- [ ] C12 `build_options`: 4 options by default; never the answer among the wrong ones; no duplicates; shape matches the answer; up to 2 common, at least 1 random; seeded order; one formatter for all; a float becomes exact where it fits (`7.4833…` → `2\sqrt{14}`).
- [ ] C13 The request contract is validated on both sides; `contract.json` staleness fails `bun run ci`; `check-compose.ts` still passes, extended to assert the `runner` drop.

**F2 L7 engine**
- [ ] C14 Migration creates §4's tables and constraints; `verification_run` rejects `UPDATE` and `DELETE` as `gem_app`.
- [ ] C15 Flow A, against recorded `gen-v8` output and a mock model: **Computed**, **Programs disagree** (fail, both shown), **Couldn't compute** (warn, `unverified`, no answer).
- [ ] C16 Flow A step 5 per type: `single_choice`, `true_false`, `numeric` (tolerance 0 for exact, 1e-6 for floats), `short_answer`; `multi_choice` can't be computable.
- [ ] C17 Anything the model states on a computable question is discarded, and a differing value is `modelClaim`; no model-written value reaches an option.
- [ ] C18 The blind request contains only the question and passage, never options, author program or a stated answer (asserted on the captured request). The blind program sees the rendered question.
- [ ] C19 Notation check: each of SPEC's four forms triggers classification; a computable result fails with the "calculation written as a concept question" reason; a symbol-only definition passes; no notation means no model call (request count asserted).
- [ ] C20 Flow B's six outcomes each have a test: Verified, Wrong answer, No match, Ambiguous, Couldn't check, Not computable (`model_agreed` or warn, never a computed pass).
- [ ] C21 Short-answer and numeric flow B compare with `correctAnswer` and `acceptedAnswers`.
- [ ] C22 Program repair: fixes each mechanical failure once, isn't tried on a timeout, denial or mistake program; a failed repair is `unverified`.
- [ ] C23 A sandbox denial fails the question and writes `verify.sandbox_denial`; an ordinary math error doesn't.
- [ ] C24 Every run writes a `VerificationRun`, with `sandboxVersion`; every model call is in `LlmCallLog` with bodies. The API never evaluates a result: `sympify`/`eval`-like use is absent from TS, and a hostile result string is stored and shown as text.

**F3 Import flow B**
- [ ] C25 **Q7:** importing the fixture, the job reports Q7 **Wrong answer** with suggested fix `-1`; the other computable questions verify. Runs against the real sandbox and a mock model with recorded programs.
- [ ] C26 The fix is applied only on confirm; rejecting keeps the error and blocks saving; no path applies it implicitly.
- [ ] C27 Saved questions carry `verification`; `TestImportRecord.report` lists accepted fixes; export round-trips and re-imports.
- [ ] C28 `verify.solve` unassigned: the UI explains it, the route answers 409, import still works.
- [ ] C29 Only the owner or an admin reads a job; authz matrix extended to every §6 route; rate limit answers 429.
- [ ] C30 Gate: default on; `blockers` lists unverified computable questions; a settings row without the key loads; turning it off is audited.
- [ ] C31 Playwright: verify → progress announced → Q7 badge in text and icon → Accept fix → save. Programs are readable; a hostile LaTeX result renders inertly.
- [ ] C32 axe reports zero violations in each new state and at 320 px; catalogs complete; `no-literal-ui-string` passes.

**Whole phase (F4)**
- [ ] C33 Eval set `l7-smoke` (`verify.solve`): blind program valid, agreement rate, repair rate, classification on labelled questions, Q7 outcome; runs on the mock in `bun run ci`.
- [ ] C34 Live on the reference model (`bun run llm:live` extended, or `bun run llm:eval l7-smoke`), `params` with thinking off, `generate-smoke` + programs + sandbox: agreement and option counts recorded in the audit and compared with the prompts doc's `gen-v8` row. **Blocked** if the box can't be reached.
- [ ] C35 Compose path, now that Docker is available: `docker compose up --build` and `bun scripts/check-compose.ts` pass on this machine, and the P1.5 e2e mock path runs; P0's A1, A2, A33 are updated in `docs/P0-audit.md`.
- [ ] C36 `verify:escape` under `runsc` passes, or is **blocked** with what unblocks it (§5, gVisor).
- [ ] C37 `bun run ci` passes from a clean clone with no model server reachable.
- [ ] C38 Every §5 decision that changed SPEC is logged in §15.2 and reflected in §3A.3.1, §4, §10, §12; the prompts doc gets the live row; `docs/DEVELOPMENT.md` covers the sandbox and escape suite.

## 9. Environment prerequisites

As P1.5, plus Docker and Compose, available in WSL. `runsc` isn't installed and isn't needed for anything but C36. Python 3.12 with pinned libraries from the micromamba env. The reference Ollama endpoint for C34 only. The role must have thinking off: pass `LLM_DEV_PARAMS='{"temperature":0.7,"top_p":0.8,"top_k":20,"presence_penalty":0,"reasoning_effort":"none"}'` in the shell, since `.env` doesn't set it.

## 10. Build and audit procedure (per feature)

For each feature, in order:

1. Build it, with its tests. A §5 decision that turns out wrong is changed here and noted for the SPEC log.
2. Run `bun run ci`. It must pass in full; fix anything it reports before going on.
3. Audit the feature's criteria from §8 and **append** a section `## F<n> <name>` to `docs/P2.1-audit.md`: pass / fail / partial / blocked with evidence (test name, command output, or file:line) per criterion, the `bun run ci` summary, and any deviations. A `fail` is fixed before the commit; a `blocked` says what unblocks it. Claims must come from a command that ran: no criterion passes on reading alone if a test can check it.
4. Commit with only that feature's changes plus its audit section: `P2.1: <feature>`, a body listing what was built, and the attribution line. Don't start the next feature with failing checks or uncommitted work.
5. If a later feature has to change an earlier one, that change goes in the later commit, and the earlier audit row is updated with a note.

Then close: run the live checks, re-run earlier criteria the later features touched, write the summary table at the top of the audit, bump SPEC (also correct its title line, which still says v0.24), add the "Last updated" entry, log §5 in §15.2, and commit `P2.1: phase audit; spec`.
