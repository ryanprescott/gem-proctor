# P2.2 – PDF ingestion with Marker (build spec)

> Companion to [`SPEC.md`](SPEC.md) (v0.28). This file says **what P2.2 builds and how it's checked**. Where the two disagree, `SPEC.md` wins. Fix the discrepancy here, or log a change in SPEC §15.
> Written for a single uninterrupted build ("zero-shot"), **one feature at a time** (§10). **Requires [`P2.md`](P2.md) to be finished.** It sits before P2.5: [`P2.md`](P2.md) §3 put PDF extraction out of scope, and this phase is where that changes.

---

## 1. Goal

A creator uploads a PDF, including a scan or a page of equations, and gets a source: Markdown with the equations as `$…$` / `$$…$$` LaTeX, the section tree, a preview they can correct, and from there the same private, versioned, embedded source as one they pasted. Nothing downstream changes: chunking, embedding, retrieval, citations, authoring and the L2 quote check all work on the Markdown, as they do today.

The conversion is done by [Marker](https://github.com/datalab-to/marker) (layout analysis, OCR for scanned pages, equation recognition) in a converter service of our own, on the Ollama box's GPU or any machine that can reach it.

Source: SPEC §3C.1 (upload), §3C.2 (ingest), §3C.5 (versioning), §11.5 (deployment), §3A.3.1 "The sandbox" (isolation, for untrusted input), §8.1 (where data goes), §1.3.

## 3. Out of scope (do not build)

Page numbers in citations (a source is cited by section, as now; the converter is asked for page count only, so a later phase can add a page map). Keeping figures: images are dropped from the text and counted in a warning. DOCX, PPTX, EPUB, HTML and image files (Marker reads them; add them when asked). Marker's `--use_llm` mode (an Ollama model cleaning up tables and equations): the first measurement decides whether it's worth a phase. Re-converting an old file with newer settings (upload again). Batch or folder upload. OCR of languages other than what Marker's defaults give. Making CPU conversion fast: it is supported and measured, and a long PDF is handled by choosing pages (below), not by tuning.

## 4. Database

```
SourceFile(id, ownerId, filename, mimeType, sizeBytes, sha256, content bytea, status: pending|converting|ready|failed,
           errorCode?, errorParams?, markdown text?, pageCount?, warnings jsonb, converter jsonb?  // { name, version, mode },
           createdAt, startedAt?, finishedAt?, deletedAt?)
SourceRevision(... sourceFileId?)   // new nullable FK: the file this revision's Markdown came from
```

- The PDF is stored in Postgres (`bytea`), so one backup holds everything and a source's origin can't go missing. The cap is an instance setting, default **50 MB**, separate from the text cap.
- `SourceFile` is soft-deleted, like sources. A file a revision points at can't be hard-deleted.
- Grants: `SELECT, INSERT, UPDATE` for `gem_app`, `DELETE` not granted. A hand-written migration, as for the other tables.
- `InstanceSettings` gains `convert: { maxFileBytes: 52428800, mode: "balanced" | "fast", maxPages: 400, device: "cpu" | "gpu" | "auto", baseSeconds: 120, secondsPerPage: 30, idleUnloadSeconds: 300 }`. A settings row without the key loads with the defaults.

## 5. Decisions made for P2.2

If one doesn't hold up, change it and log it in SPEC §15.2.

| Decision | Choice | Resolves |
|---|---|---|
| Our own converter service | A small FastAPI app of ours around Marker's Python API, not Marker's bundled `marker_server` | The bundled server takes a path on its own disk, not an upload, and its README calls it small-scale and not very robust; it doesn't expose the options we need |
| Where it runs | The base case needs no GPU and no other machine: the converter runs in the Compose stack (profile `convert`) on the CPU and system RAM of the host that runs the API, and the PDF never leaves it. With a GPU it is faster, and then it can run on the Ollama box (or any machine with the card), reached at `CONVERT_URL` from the API. Unset: PDF upload is refused with `convert_unavailable` and the rest of the app is unaffected | §11.5 |
| Marker's GPU path | Check Marker's installation notes at the start of F1: its README now describes an NVIDIA path that runs its own inference server in Docker, and a CPU path through llama.cpp. Pin the version (`requirements.txt`), and record how it was installed in `docs/DEVELOPMENT.md` | The README is the only source this was written from |
| Device | Ingest is passive and the rest is interactive (generation, review, results), so conversion never competes with them. `convert.device` is `cpu` (default), `gpu` or `auto`: `cpu` leaves the card to the models people wait on, and `gpu` is for an operator who has a card that nothing interactive uses. The service reports the device it uses in `/health`. Measured first, in a spike at the start of F1, on both: seconds per page of the text PDF and of the scan, peak RAM, and peak VRAM. A GPU conversion unloads Marker's models after an idle time (`idleUnloadSeconds`, default 300), so a shared card is free between conversions. **No step ever unloads or delays the generation model**: an earlier idea, asking Ollama to unload before converting, is dropped, because it costs the next generation an 8 s reload. A conversion that runs out of memory (VRAM or RAM) fails with `convert_failed` and a retry | Interactive speed first; a slow background job is fine |
| Contract | Zod in `packages/shared/src/convert.ts` is the source; JSON Schema exported to `apps/convert/gem_convert/contract.json`, staleness-checked by the existing export step, as for `apps/verify` | §3A.3.1 |
| Request | `POST /convert`, multipart: `file` (the PDF) and `options` (`mode`, `pageRange?` (e.g. `5-23`, one chapter of a textbook), `forceOcr?`). Reply: `{ markdown, pageCount, figures, warnings[], converter: { name, version, mode } }`. The reply is capped (16 MB) and validated with Zod before anything stores it | §3A.3.1 "Results" |
| Untrusted input | A PDF is untrusted input to a parser with a large native surface. The converter container: no environment secrets, read-only root, a `tmpfs` work directory, no capabilities, `no-new-privileges`, `pids`, memory and CPU limits, and on a network that reaches only the API. GPU passthrough weakens isolation (no gVisor): the VM is the next wall, stated in SPEC §15 | §3A.3.1 |
| Worker lifecycle | Marker's models stay loaded in one worker process. A conversion is given `convert.baseSeconds + convert.secondsPerPage × pages` (defaults 120 and 30 on the CPU, 10 on a GPU, set from the first measurement); over that, the worker is killed and the service starts a fresh one; so does a crash, an out-of-memory kill, or every 200 conversions. The API sees `convert_timeout` or `convert_failed`, with a retry. The creator sees elapsed time and, if the service reports it, the page being read | §3A.3.1 "Recycling" |
| Low priority | The converter container runs at the lowest CPU priority (`nice` 19, a `cpus` limit, and Marker's thread count capped to match, defaults 2 CPUs and a `mem_limit` of 6 GiB, set from the spike), so a conversion can't starve the API or Postgres: it takes what's idle. Its jobs run on their own queue and never block `llm.generate`, `authoring.l7` or `source.embed`. The page says the conversion is running in the background and that the creator can leave; the Sources list shows `Converting` and the live region announces completion if they're still on the page | Interactive speed first |
| Privacy | The PDF goes to the converter and nowhere else. With "local endpoints only" on (§8.1), `CONVERT_URL` must resolve to a loopback, private or Tailscale address, or upload is refused with `convert_remote_blocked` | §8.1 |
| Pipeline | Upload creates a `SourceFile` and queues `source.convert`. A `ready` file has Markdown and warnings; the creator edits it, and **Save** makes a source (or a new revision) with `format: "markdown"`, the edited text, and `sourceFileId`. From there it is the P2 path, unchanged. A file is private to its owner: another user gets 404 | §3C.1, §5 |
| Clean-up of Marker's output | In `packages/knowledge`, pure functions with tests: display math to `$$…$$` on its own lines, inline to `$…$`; `<math>` and `\(…\)` forms rewritten to the same; image links removed and counted; empty headings and repeated running headers or footers dropped; `$` in prices left alone. Nothing is rewritten that changes what an equation says | §3C.1 |
| Warnings | Computed by us, on top of `previewSource`'s: `figures_dropped` (count), `low_text` (fewer than 200 characters per page: probably a scan that didn't read), `unbalanced_math` (a `$` or `$$` left open), `math_unparsed` (KaTeX fails on it, found in the browser and shown in the preview), `pages_skipped` (over `maxPages`) | §3C.1 |
| Size and shape | Over `maxFileBytes`: 413 `convert_too_large`; not a PDF by its first bytes (`%PDF-`), whatever its name or type: 415 `source_bad_type`; encrypted or damaged: `convert_bad_pdf`; nothing readable came out: `convert_empty` | §3C.1 |
| Progress | SSE on `/sources/files/:id/events`, as for embedding: the state is in the database, and a dropped stream loses nothing. Announced through the live region | §11.2, §1.3 |
| Audit | `source_file.upload`, `source_file.delete` (target `source_file`); the conversion's own outcome stays on the row | §1.3 |
| Rate limits | The upload and retry routes | §11.2 |
| Mock | `packages/convert/mock` (a Bun server like `packages/llm/mock`) answers `/convert` and `/health` with canned Markdown, with a delay and failure switches, so no test needs Marker or a GPU | §3B.4 |
| Fixtures | `tools/fixtures/make-pdfs.ts` renders the repo's `linear-algebra.md` to a text PDF with the Chromium Playwright already installs (KaTeX-rendered, so the equations are real glyphs), then rasterizes its pages into an image-only PDF: the "scan". Both are committed (small), with the expected LaTeX list | S8 |

## 6. Routes in P2.2

All under `/api/v1`. New: `POST /sources/files` (multipart; rate limited), `GET /sources/files/:id`, `GET /sources/files/:id/events` (SSE), `POST /sources/files/:id/retry`, `DELETE /sources/files/:id`, `GET /sources/files/:id/original` (the PDF, with `content-disposition: attachment`). Changed: `POST /sources` and `PUT /sources/:id` take an optional `fileId`, and then `text` is the Markdown the creator saved. `/health` gains `convert: { ok }` when `CONVERT_URL` is set. SPEC §12 and the authz matrix are extended; a source file is object type `source` (private to its owner, an admin may read).

Web: the **Sources** page's add form gains "PDF" next to paste and `.md`/`.txt`; a source's page shows its original file (download) and the conversion's warnings.

## 8. Acceptance criteria (the audit checklist)

Each line is checked by a test, a command, or reading the code. The audit marks each **pass / fail / partial / blocked / dropped** with evidence. All earlier criteria must keep passing, P2's included.

**F1 Converter**
- [ ] M1 `GET /health` says whether the models are loaded and what version of Marker runs; `POST /convert` takes a PDF and options and returns a reply that validates against the contract.
- [ ] M2 The contract's JSON Schema is exported and staleness-checked; the converter validates requests against it, and the API validates replies.
- [ ] M3 One conversion at a time: a second request waits, and `/health` answers while one runs.
- [ ] M4 Caps: a file over the size, a document over `maxPages`, a request that isn't a PDF by its first bytes, and a reply over 16 MB each end in their error code, and the next request still works.
- [ ] M5 A conversion over the time limit kills the worker and a new one starts; so do a crash and the Nth conversion; the next conversion gives a correct result.
- [ ] M6 The container is isolated as §5 says, checked by a script (`scripts/check-convert.ts`, as `check-compose.ts` is for verify): read-only root, no capabilities, no secrets in its config or environment, limits, reachable only from the API's network.
- [ ] M7 A hostile PDF set (malformed xref, a decompression bomb, a page count of millions, an embedded file, JavaScript, a link to a URL) fails or converts inertly: nothing is fetched, nothing runs, and the service is healthy after.
- [ ] M8 The mock answers the same contract, with a delay and each failure, and `bun run ci` needs no GPU and no Marker.
- [ ] M9 Marker's install is written in `docs/DEVELOPMENT.md` and pinned, for the CPU in Compose and for a GPU. The spike's numbers are in the audit: seconds per page on CPU and GPU for the text PDF and the scan, peak RAM, and peak VRAM. `convert.device`, the GPU idle unload and the per-page time limit are each tested.
- [ ] M9a Interactive speed holds during a conversion: with a CPU conversion of the text PDF running, `GET /health`, a practice route and an authoring session read each answer with a p95 within 2× of the same routes idle (measured, in the audit); and a generation call started during a conversion takes no longer than one started idle, within noise. The converter's container limits are checked by `scripts/check-convert.ts`.

**F2 API**
- [ ] M10 Migration creates `SourceFile` and `SourceRevision.sourceFileId`; `DELETE` is refused for `gem_app`; the grants hold.
- [ ] M11 Upload stores the PDF with its hash, queues `source.convert`, and returns the file; a type or size problem is its error code, and nothing is stored.
- [ ] M12 The job runs the conversion and stores the Markdown, the page count, the warnings and the converter's version; a failure stores its code and can be retried; a `converting` file left by a stopped API shows as failed.
- [ ] M13 Progress over SSE: events arrive; a reconnect recovers the state; authz holds.
- [ ] M14 Clean-up: each rule has a passing and a failing case, including the `$` in a price and an equation that must not change.
- [ ] M15 Warnings: each of the five, with a case that raises it and one that doesn't.
- [ ] M16 Save: `POST /sources` and `PUT /sources/:id` with `fileId` make a revision with `sourceFileId` and the saved text; another user's file is 404; a file that isn't `ready` is 409.
- [ ] M17 Everything downstream is unchanged: a converted source is chunked, embedded and retrieved; a quote from an equation-bearing chunk passes L2; the P2 suites pass.
- [ ] M18 Privacy: files are private (404 for another proctor, 403 for students, an admin reads); with local-only on, a remote `CONVERT_URL` refuses upload; with `CONVERT_URL` unset, upload is `convert_unavailable`.
- [ ] M19 Audit rows for upload and delete; the authz matrix covers every new route; `/health` reports the converter.

**F3 Web**
- [ ] M20 Playwright, against the mock: choose a PDF, watch progress (announced), see the Markdown preview with equations rendered as MathML and the warnings, edit, save, and reach the source page with its original downloadable.
- [ ] M21 A failed conversion shows its reason in words and a retry; a scan with `low_text` says so.
- [ ] M22 `math_unparsed` is found in the browser and shown with the equation's text.
- [ ] M23 Keyboard only, through the whole flow, with announcements.
- [ ] M24 axe clean in every state and at 320 px.
- [ ] M24a A page range limits what is converted and what is billed against `maxPages` and the time limit; an invalid range is refused before anything is stored.

**Whole phase (F4)**
- [ ] M25 The fixtures exist and are reproducible (`tools/fixtures/make-pdfs.ts`), and say what the right answer is.
- [ ] M26 `convert-smoke` (an eval set: the text PDF and the scan through `/convert`): headings recovered, equations found (a normalized comparison with the expected LaTeX), and text similarity to the original Markdown. On the mock in `bun run ci`; live on the box otherwise.
- [ ] M27 Live, end to end on the reference box: upload the text PDF and the scan, preview, save, and author a question from an equation-bearing passage with the quote passing L2. Rates, seconds per page and failures recorded in the audit. **Blocked** if the box can't be reached.
- [ ] M28 SPEC §13 gets what M27 measured (equation accuracy, scan quality, VRAM), and says whether `--use_llm` is worth a phase.
- [ ] M29 `bun run ci` passes from a clean clone with no converter and no model server reachable; `no-literal-ui-string` and catalogs pass.
- [ ] M30 Every §5 decision that changed SPEC is logged in §15.2 and reflected in §3C, §10, §11.5, §12, §14; `docs/DEVELOPMENT.md` covers the converter.

## 9. Environment prerequisites

As P2. Postgres with pgvector, Python 3.12 for the converter's own tests, the Playwright Chromium for the fixtures. Marker and its models only on the GPU box, for M9 and M27, with the model weights downloaded there; nothing else in `bun run ci` needs them. The reference Ollama endpoint stays as it is.
